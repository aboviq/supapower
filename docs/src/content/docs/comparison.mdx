All five solve the same problem - read and write locally, converge later - and differ in what you
have to run, what the client stores, and who decides what a client may see. One note before the
table: Supapower builds on [PGlite](https://pglite.dev/), which is an Electric SQL project, but
does **not** use Electric's sync service - the two are unrelated beyond sharing that dependency.

## Reading the table

**[RxDB](https://rxdb.info/replication-supabase.html)** with its Supabase replication plugin is the
closest architectural match, and the reason the first two rows of the table look identical: it also
talks straight to Supabase over PostgREST and Realtime, so "nothing to deploy" is not unique to
Supapower. What differs is the local database and the conflict model. RxDB is a document store
queried with Mango-style selectors - no SQL, no joins, no Postgres - and conflicts are resolved per
document, where [the default handler](https://rxdb.info/transactions-conflicts-revisions.html#custom-conflict-handler)
drops the local version in favor of the server's and merging two edits means writing a handler
yourself. It also asks your Supabase tables for string primary keys and `_deleted` / `_modified`
columns. Choose it for a document model, React Native, or one client syncing several kinds of
backend. Choose Supapower to keep writing SQL against a real Postgres and to get column-level
merging without writing the merge.

**[PowerSync](https://www.powersync.com/)** is the closest relative in intent and Supapower's stated
inspiration - it's also
[Supabase's own listed offline-first integration](https://docs.powersync.com/integrations/supabase/guide).
Choose it for non-Supabase or non-Postgres backends, native mobile SDKs, [Sync Streams](https://docs.powersync.com/sync/streams/overview)
that carve a large table into per-user buckets, or paid support and uptime SLAs. Supapower's trade:
no service to run, no replication slot on your database, and RLS instead of a second rules
language to maintain.

**[Electric](https://electric.ax/sync/)** is a read-path sync engine: [Shapes](https://electric.ax/docs/sync/guides/shapes)
delivered over HTTP and cached by a CDN, deliberately leaving [writes](https://electric.ax/docs/sync/guides/writes)
to the application to design. Choose it for large read-heavy fan-out, or a Postgres that is not
Supabase. Supapower ships the write path instead - the queue, the retries, the per-column conflict
rules - so there's nothing left to build.

**[Zero](https://zero.rocicorp.dev/)** syncs whatever a [query](https://zero.rocicorp.dev/docs/queries)
asks for and applies writes through server-authoritative [mutators](https://zero.rocicorp.dev/docs/mutators) -
closest to "your backend, but instant". Choose it when authorization and mutation logic belong in
server code and the working set is a query, not a table. Supapower's authorization is the
database's own: no second permission model to write.

## Partial sync in detail

In every case it does come down to a filter attached to a table - what differs is who writes the
filter, and whether a client can change it at runtime.

- **RxDB** - the Supabase plugin takes a `pull.queryBuilder`, so the pull is an ordinary PostgREST
  query you can narrow (`query.eq('status', 'active')`) or point at joined tables. The filter lives
  in client code, so RLS is still what stops a client from asking for more. See
  [Supabase replication](https://rxdb.info/replication-supabase.html).
- **PowerSync** - a stream is a SQL-like query in a YAML config deployed to the service, e.g.
  `SELECT * FROM lists WHERE owner_id = auth.user_id()`. Filters take parameters from the token,
  the connection or the client's own subscription, and each distinct parameter value becomes a
  bucket that syncs as a unit. See [Sync Streams](https://docs.powersync.com/sync/streams/overview).
- **Electric** - a shape is one table plus an optional `where` clause and `columns` list, requested
  over HTTP; subqueries cover membership and sharing rules
  (`id IN (SELECT user_id FROM memberships WHERE org_id = $1)`). Shape definitions are immutable,
  and production apps are expected to have their backend issue them so a client cannot widen its
  own filter. See [Shapes](https://electric.ax/docs/sync/guides/shapes).
- **Zero** - filters are ordinary queries in application code. `zero-cache` asks your server to
  resolve each query by name, which is where it can be narrowed further for permissions, and a
  query can pull in relationships, so the unit is a query result rather than a single table. See
  [Queries](https://zero.rocicorp.dev/docs/queries).

Supapower has no equivalent knob. A tracked table is downloaded whole - the request selects the
columns the local schema knows, orders by primary key and pages through, narrowed only by the
[`cursor`](/packages/supapower/#table-cursor-configuration) watermark, which limits how far back in
time it reads rather than which rows qualify. The realtime subscription binds to a schema and table
with no filter either.

What a client actually ends up holding is whatever its RLS policies return, so the lever for "this
client should only have its own rows" is the policy, not a per-client filter. When a table is
bigger than the narrowest slice a policy can express, the workaround is to split the hot subset
into its own table - optionally in a
[separate schema](/packages/supapower/#table-schema-configuration) - and track that instead.

## Also in the field

- [WatermelonDB](https://watermelondb.dev/) - a SQLite-backed reactive database for React and
  React Native; you implement the sync backend yourself against its pull/push protocol.
- [LiveStore](https://docs.livestore.dev/) - an event-sourced SQLite store with pluggable sync
  backends (Cloudflare Durable Objects first-party).
- [Triplit](https://www.triplit.dev/) - a full-stack syncing database with CRDT-based conflict
  resolution, requiring its own server (`@triplit/server`).
- [Verdant](https://verdant.dev/) - an IndexedDB store plus a small Node and SQLite sync server of
  its own, MIT-licensed and openly experimental; it replaces the backend rather than syncing an
  existing Supabase one, which is why it is not in the table above.
